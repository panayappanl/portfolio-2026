OpsXpress · EmmaCare

Making standards stick in a 120K-line codebase

Moving a growing React app to a feature-based structure, with rules that CI enforces instead of people.

Rules in CInot in a wiki

The problem

Ten engineers were adding code to a type-based layout (components/, utils/, services/). Related code lived far apart, features leaked into each other, and the same review comments came up on every PR.

What I did

  • Reorganised the app by feature, each module owning its components, hooks, queries and tests.
  • Set strict TypeScript and shared ESLint rules, including import boundaries between features.
  • Turned the rules into CI checks so a PR that breaks them cannot merge.
  • Wrote the conventions into the Claude Code project rules, so AI-generated code follows them by default.

Trade-off

A full restructure would have stalled feature work, so we moved one feature at a time, starting with the most active areas.

Standards now hold without reminders, and reviews focus on logic and design instead of style and structure.
OpsXpress · EmmaCare

A design system built from zero

Replacing one-off styling with shared tokens and accessible components used by three products.

35+ componentsacross 3 products

The problem

Every screen styled its own buttons, forms and tables. The products looked slightly different from each other, and simple UI changes had to be made in many places.

What I did

  • Defined design tokens for colour, type and spacing with the design team.
  • Built accessible primitives first (inputs, buttons, dialogs), then composed forms, tables and layouts from them.
  • Documented every component in Storybook with usage examples.
  • Made the design system the default for all new UI, and moved older screens over as they were touched.

Trade-off

I kept the first version small and opinionated. Fewer components with clear rules got adopted faster than a large library with many options.

35+ components, used across 3 products serving multiple US healthcare providers.
OpsXpress · AI workflows

Giving developers domain knowledge through MCP

Developers often picked up healthcare tickets without knowing the business rules behind them.

Context firstbefore code

The problem

Healthcare workflows have rules that are not obvious from the code. Developers worked from the ticket alone, then went back to product managers with questions, or shipped something that missed an edge case.

What I did

  • Built an MCP server that connects Claude Code to feature docs, business rules and past tickets.
  • Developers ask questions like "what happens when an appointment is cancelled?" while working, and get answers with links to the source.
  • Combined it with the /start-ticket skill, so each ticket starts with domain context, affected files and a draft plan.
  • Paired it with an impact tool that maps a change to the components and pages that depend on it, so developers know what to test.

Trade-off

AI answers are only as good as the docs behind them. Keeping the source documents up to date became part of the definition of done.

Fewer clarification loops with product managers, and new developers contribute to complex areas sooner.

A public demo with a sample clinic domain is in progress.

OpsXpress · EmmaCare

Redux to TanStack Query

Separating server state from client state, and removing the code that existed only to fetch data.

~8K linesof boilerplate removed

The problem

Each API call needed action types, thunks, reducer cases and selectors. The same data was fetched repeatedly on the dashboard, and stale data was a common bug.

What I did

  • Moved server data to TanStack Query and kept Redux only for true client state.
  • Introduced a query-key factory and a standard hook pattern per feature, like useAppointmentsQuery.
  • Used caching, request deduplication and targeted invalidation after mutations.
  • Migrated feature by feature, with old and new patterns running side by side.
~8K lines of boilerplate removed, and duplicate API calls on the main dashboard cut roughly in half.
SLK Software · Emerson

Keeping APIs fast at peak traffic

Node.js APIs slowed down when traffic peaked, because every request went to the database.

450 → 160msat 2K+ requests/min

The problem

At busy hours, response times climbed to around 450ms. Most requests asked for the same data that rarely changed.

What I did

  • Profiled the busiest endpoints to find the read-heavy, rarely changing data.
  • Added a Redis cache in front of those reads, with expiry times matched to how often each data type changes.
  • Cleared the related cache entries on writes, so users never saw outdated data after an update.

Trade-off

Caching everything would have been fast but risky. I only cached data where a short delay in freshness was acceptable.

Latency dropped from 450ms to 160ms on APIs serving 2K+ requests per minute.

How I lead

The habits behind the results above.

Standards live in tooling

If a rule matters, CI checks it. Lint rules, type checks and AI review handle consistency, so people don't have to remember it.

Reviews are for decisions

Formatting and common mistakes are caught before a human looks. Code review time goes to design, edge cases and teaching.

Context before code

A developer who understands the business rule writes better code than one who only has the ticket. Domain knowledge should be one question away.

Scope early with clients

Most delivery problems start in the requirement call. Clear tickets and honest estimates up front cut mid-sprint changes from about five to one.
